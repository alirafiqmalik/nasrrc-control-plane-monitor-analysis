# Map — live-analyzer

## Notes

- Offline capture/decode scripts lifted from `baseband-attach/scripts/` and pointed at a local `.venv`.
- Summary-line classifier in `src/nasrrc/` proven against `fixtures/example-lte/LTE_full_summary.txt`.
- Live host path is **tail the ring over adb**, not `scat -s /dev/umts_dm0` on the host.

## Decisions-so-far

- GSMTAP host flag is `-H`, not `-a`.
- Dump name must contain `.sdm` for the logger parser.
- First live implementation: FIFO + `adb exec-out tail -f sbuff_*.sdm`. Device proof is ticket 01.
- Default run is continuous until Ctrl-C. `--airplane` is optional. No eSIM on/off.
- Keep the repo simple (ADR-0001).
- Handover vs generic reconfiguration is deferred to dissected-field analyzers (ticket 02).
- 2026-09-02 device proof stopped at the first gate: both modem logging enable properties became `true`, but `vendor.sys.modem.logging.status` stayed `false`, no `dmd` process opened `/dev/umts_dm0`, and the newest timestamped ring (`/data/vendor/radio/logs/always-on/sbuff_20260901230105.sdm`) remained at 6,016,827 bytes with a 2026-09-01 23:01:09 mtime. Android init showed the logging-control services running; the kernel reported that `umts_dm0` was not open. The props were restored to `false`. A reboot or a successful on-device Verbose Vendor Logging toggle is needed before the remaining proof can run.
- The same attempt confirmed that a FIFO named `.sdm` enters SCAT's logger path (`read_dump` → `run_logger`), rather than raw SDM. It decoded the stale `sbuff_power_on_log.sdm`, but that does not prove live delivery. Host tshark needs `lte_rrc` (underscore) on this installation and needs elevated capture permission. Latency and startup-frame integrity (truncation or garbling) are not measurable until the ring grows.
- After the reboot, verbose logging created `/data/vendor/slog/sbuff_20260902035852.sdm`; it grew from 0 to 4,853,568 bytes between 03:58:52 and 03:58:56 before rotating into `always-on`. The first post-reboot script run missed this burst because it waited three seconds and watched the newer `sbuff_power_on_log.sdm`; the selector now starts immediately and excludes the power-on/profile artifacts. A further reboot is needed to exercise the corrected live path because later enable attempts did not start another session.
- On the next reboot, the corrected guard selected `/data/vendor/slog/sbuff_20260902040835.sdm`, and SCAT again entered `run_logger`. The device then rotated the file into `always-on`; remote `tail -f` exited, so `wait -n` restored logging instead of maintaining the stream. The FIFO writer now follows each new timestamped session filename while ignoring the same file's move between directories. Live UDP and latency still need a fresh post-reboot session.
- The physical T-Mobile SIM is slot/radio 0 (`LOADED`, PLMN 310260); slot 1 is `NOT_READY`. SCAT sends radio 0 to the configured GSMTAP host (`127.0.0.1`) and any second radio to the subsequent address, so the tshark listener filters on destination `127.0.0.1` to exclude eSIM traffic without toggling airplane mode.
- The rotation follower was not actually following. `tail -f` never returns on a ring that stopped growing, so the stream stayed pinned to the ring it started on and died at the first rotation (measured: packets stopped 10 s after the first ring was replaced). The remote tail now runs in the background and is swapped for the newer session; `tests/test_live_tail_ring.sh` fails against the old shape and passes against the new one.
- Killing `adb exec-out` on the host does not kill the on-device `tail`. Five leaked remote tails had accumulated across earlier attempts. Start and stop now reap them with `pkill -f 'tail -c .1 -f /data/vendor/'`.
- `cleanup` blocked in `wait` on a child that ignored the signal, so logging was never restored. It now kills, waits a second, `kill -9`s, and restores regardless.
- The startup growth guard rejected a healthy device. Under a short rotation interval (~9 s observed) the newest ring is replaced before it is ever seen to grow in place, so a newer session name now counts as growth.
- SCAT emits GSMTAPv3 for 5G NR. Wireshark 4.7.2 here has no v3 dissector and renders those as `Unknown GSMTAP version (3)`, so the documented display filter showed nothing while the phone was on NR even though packets were arriving. The filter now leads with bare `gsmtap`.
- The on-device logger allows roughly one session per boot: after `start modem_logging_stop` no `start modem_logging_start` brings it back, and `vendor.sys.modem.logging.status` stays false until a reboot. Plan one live run per boot. `sys.boot_completed` also reads true from the pre-reboot system, so a reboot must be waited out by disconnect, not by that property.
- With the rotation-safe stream still attached, `start modem_logging_start` flushed the next buffered ring without changing radio state. SCAT immediately emitted physical-radio traffic on `127.0.0.1:4729`: LTE RRC DL/UL DCCH, LTE paging, and NR RRC. The ring follower now requests that next flush itself whenever the previous timestamped ring has rotated.
- Measured latency, 2026-09-02 `--airplane` proof run: SCAT opened the FIFO at 06:32:34.154 and the first GSMTAP packet reached tshark at 06:32:36.900 — **2.75 s from attach to first packet**, 5.71 s from launching the script. In steady state packets arrive in bursts 5.5–6.6 s apart, matching the ring rotation cadence, so end-to-end lag is bounded by how often dmd rotates rather than by the tail loop. A 22 s gap covers the airplane cycle itself.
- `tail -f` keeps SDM framing intact across a rotation: SCAT logs one `Skipping packet as magic does not match` at each splice and resyncs, and keeps decoding radio 0 afterwards.
- `adb_su` wraps its argument in single quotes, so any helper argument that carries its own quotes collapses on the device. `pkill -f 'tail -c .1 -f /data/vendor/'` arrived as `pkill -f tail -c .1 -f /data/vendor/` — six tokens, the qualifier dropped, matching every unrelated `tail` on the phone. The reap pattern is now space-free and quote-free (`tail.-c..1.-f./data/vendor/`), verified on device to kill the three ring tails and spare an unrelated `tail -f /data/local/tmp`.
- Restoring logging now happens first in `cleanup`, and interrupts are ignored for the rest of teardown: a second Ctrl-C used to land in the kill grace period and leave `persist.vendor.verbose_logging_enabled` true.
- The follower publishes its `adb exec-out` pid to a file, because `stream_rings` is a subshell and only notices TERM after its `sleep` returns — longer than cleanup's grace, which orphaned the host process.
- Ring selection is monotone by session name. `ls -1t` is mtime order, and a ring still being flushed can outrank the session that replaced it; reattaching backwards would replay its whole history as fresh GSMTAP. `latest_ring` now sorts basenames on the host and prefers `/data/vendor/slog/` over the always-on copy.
- Ticket 01 resolved: live GSMTAP until Ctrl-C, optional `--airplane`, restore-on-stop. See `.scratch/live-analyzer/issues/01-prove-tail-the-ring.md`. Offline decode of the proof ring `sbuff_20260902063215.sdm` starts with one `Skipping packet as magic does not match` (mid-packet join) then 40 GSMTAP frames (NR RRC UL/DL DCCH + BCCH, NAS-5GS). LTE MIB from `sbuff_20260902062550.sdm` still dissects as GSMTAPv2. Sample pcaps: `captures/ticket01/` (untracked). The latency number in this map is attach-to-first-packet (2.75 s) plus rotation cadence, not dmd-flush-to-tshark for a named radio event.
- Ticket 02 resolved: `src/nasrrc/fields.py` reads tshark PDML instead of the Info column, so a measurement report arrives with its measId, the reporting event behind that measId, and per-cell RSRP/RSRQ, and a reconfiguration is only called a handover when it carries `mobilityControlInfo` (LTE) or `reconfigurationWithSync` (NR). `scripts/live_analyze.sh` is the consumer; `scripts/live_replay_sdm.sh --analyze` feeds it from a dump. See `.scratch/live-analyzer/issues/02-handover-measurement-analyzers.md`.
- PDML, not `-T fields`. Flat fields flatten the tree: `lte-rrc.reportConfigId` occurs once per reportConfigToAddMod **and** once per measIdToAddMod, so the measId → A3/B1 mapping cannot be recovered from occurrence order. PDML keeps the nesting and still streams packet by packet under `-l`, so the same parser serves a file and a live interface.
- The measId → event mapping lives in the earlier RRCConnectionReconfiguration, not in the report. `Analyzer` remembers reportConfigId → event and measId → reportConfigId across packets and annotates later reports; `measIdToRemoveList` drops the entry again.
- No host capture rights here: `/usr/bin/dumpcap` is `root:wireshark` mode 0754 and this user is not in `wireshark`, so `tshark -i lo` fails with "Couldn't run dumpcap in child process: Permission denied" — for a named pipe too. `tshark -r <fifo>` bypasses dumpcap entirely and streams as the writer writes, which is why `--analyze` hands SCAT `-F <fifo>` rather than `-H`.
- `proc.terminate()` alone hangs a tshark that is blocked writing into a full pipe: it never reaches its own signal handler. The reaper closes the read end first, then waits with a timeout and kills.
- Analyzer development needed a capture, and real ones are untracked. `fixtures/synthetic-lte/make_pcap.py` hand-encodes UPER LTE RRC (measConfig with A3 and B1, a measurement report with serving and two neighbours, a handover command, a plain reconfiguration) plus NAS attach, identity and TAU, and tshark dissects all twelve frames without an expert warning. One deviation from the published grammar: Wireshark's `MeasResults` has **two** root optional bits before `measId`, and only the second gates `measResultNeighCells`.
- The real ticket-01 captures behave as expected against the analyzer: `lte-mib-and-nr.pcap` yields nothing (MIB is BCCH, which the analyzer drops along with paging), and `proof-session.pcap` yields nothing because it is GSMTAPv3.
- Three failures the ticket-01 follower could still hit, found by review and covered by `tests/test_live_tail_ring.sh`: `latest_ring` returns 1 when the device has no ring, and under `set -e` that aborted before the "enable Verbose Vendor Logging?" message could print; `ring_size` was unguarded at startup, so a ring that rotated away between `latest_ring` and the `stat` ended the run — at a ~9 s rotation interval that is routine, and it costs a reboot. Rotation now reaps only the ring it is leaving rather than sweeping the device.
- A watchdog on the remote tail is not worth building. Measured on the device: killing the on-device `tail` leaves its `sh -c su -c ...` wrapper alive, so the host `adb exec-out` survives and a host-side liveness check never fires; and a device-side `pgrep -f` matches its own wrapper's cmdline, so it always reports a hit — the "absent ring" probe returned three pids. The stream recovered by itself at the next rotation, costing one rotation interval. A guard was written, proved ineffective on the phone, and removed.
- 2026-09-02 device run, ticket 02 end to end. Modem logging was already running when the session started, rotating a 52 MB ring every ~30 s. `live_tail_ring.sh` followed six rotations (`sbuff_20260902094949` through `...095814`) with exactly one remote tail alive throughout and no accumulation; stop restored `persist.vendor.verbose_logging_enabled` to false and left no remote tails, no host processes, and no FIFO. 425 GSMTAP packets were received on `127.0.0.1:4729` by a plain UDP socket — that needs no capture rights, unlike tshark on `lo`, and is the way to watch the stream on this host.
- Those 425 packets yield 81 events: 63 measurement reports, 9 reconfigurations, 9 completes, and **zero handovers**, which is right for a stationary UE. The measId → event correlation works against a live network: the network re-issues the NR measurement config every minute or so (`configures measId26=a1,measId27=a2,measId28=a5,measId29=a5`) and the next report comes back `measId=26 trigger=a1`. LTE `measId=5` was configured before the capture opened and correctly carries no trigger.
- NR is no longer unproven. This Wireshark **does** dissect the NR RRC that SCAT emits — `nr-rrc` measurement reports appear as GSMTAPv2 — and only the NR frames of the ticket-01 proof ring were v3. Real EN-DC reports carry two `MeasResultServMO` entries for the same PSCell (servCellId 7 and 8), which is why the analyzer reports every serving MO and tags each with its servCellId rather than taking the first.
- NR spells the reported quantities `nr-rrc.measQuantityResults.rsrp` / `.rsrq` / `.sinr`, not `rsrp-Result`. The 38.133 conversions check out against Wireshark's own labels on device data: rsrp 43 → -114 dBm, rsrq 63 → -12.0 dB, sinr 64 → 8.5 dB. The LTE conversion cross-checks against SCAT's own PHY log, which reported the serving PCI 90 at -105 to -113 dBm over the same window.
- An LTE `RRCConnectionReconfiguration` carrying an embedded NR reconfiguration (EN-DC) shows the nested `nr-rrc` protocols as `hide="yes"` in PDML, so skipping hidden protocols keeps the message classified as the LTE reconfiguration it is.
- Ticket 03 resolved, and it changes the picture: `/dev/umts_dm0` **mirrors** the live SDM stream to a second reader while dmd holds it. dmd's ring still grew 14,685,987 → 20,981,219 bytes over a 25 s window in which the tap took 9.1 MB, so nothing is stolen. `scripts/experiment_scat_diag.sh node` reads the node over adb into a `*.sdmraw` FIFO and hands it to SCAT's `run_diag`; a 60 s run with dmd untouched produced 30 GSMTAP frames (RRC reconfiguration/complete, measurement reports, paging, SIB3/4/5/8/15/24, MIB, detach request, service accept). See `.scratch/live-analyzer/issues/03-scat-owns-diag.md`.
- The node tap is continuous where the ring path is bursty. Median inter-arrival 44 ms, longest gap 8.1 s on an idle stationary UE, against the ~30 s rotation cadence that bounds `live_tail_ring.sh`. First packet ~3 s after attach, about the same as the ring path's 2.75 s. What changes is everything after the first packet.
- The node returns 0 bytes rather than blocking when its queue is empty, so a single `cat` exits within milliseconds and reports nothing on a link carrying 700 KB/s. The tap has to re-run `cat` in a loop; measured about 5 iterations a second under load, which is cheap.
- `adb shell -T "su -c '...'"` delivers **zero bytes** to the host when stdin is a terminal, while the same tap on the device is plainly reading. `< /dev/null` fixes it (3.6 MB in 8 s). This cost two runs that looked like a dead radio.
- SCAT cannot drive the node itself. Its `init_diag` frames arrive intact — the exact 20-byte `CONTROL_START` was read back off the far end of the pty bridge — but the modem answers nothing whether dmd is stopped or running. dmd starts the DM session over the vendor RIL path instead: it links `liboemservice.so` and registers an OEM service (`OEM_OnRequest`, `COMMAND_SET_DM_MODE`, `COMMAND_STOP_DM`). Writing SDM control frames to the char node is inert, and `--start-magic` was never the variable.
- The init service is `DM-daemon`, the process is `dmd`, and `stop dmd` is a silent no-op. `stop DM-daemon` works and init restores it with `start DM-daemon` — but it costs the boot's logging session: the daemon comes back, `vendor.sys.modem.logging.status` stays false, and no ring is written until a reboot. Measured twice.
- USB DM is unreachable on this phone, and not for want of the function. `dm.gs7` exists in configfs (`init.gs201.usb.rc:58`) and dmd has a `UsbAgent` on `/dev/ttyGS1`, but `android.hardware.usb.gadget-service`'s `getVendorFunctions()` (`0x9590`) reads `ro.build.type`, matches `user`, and returns before it ever reads `persist.vendor.usb.usbradio.config` or `vendor.usb.config`. The value it would want is exactly `dm` (`0x80c4`: length 2, `cmp` against `0x6d64`). Setting the property and restarting `usbd` re-enumerated as `18d1:4ee7` with `ffs.adb` alone, as predicted. `scat -u` stays untested until a userdebug build.
- `vendor.sys.modem.logging.status` is not a readiness signal and cost four runs. Measured 2026-09-02: it read `true` three seconds after the enable and stayed true for 80 s while no timestamped ring was ever created and the DM node handed the tap 0 bytes — dmd was still filling `sbuff_power_on_log.sdm` towards its ~10.5 MB cap. The gate is a session ring under `/data/vendor/slog`. With one present the same tap delivered 74,547,085 bytes in 60 s. `live_tail_ring.sh` already gates on ring growth and was never exposed to this.
- A dry tap and a decoder that emitted nothing produce an identical empty pcap. `node` counts the bytes it received and reports which happened at stop, because guessing between them wasted three device runs and a reboot each.
- The first real handover. The 2026-09-02 node capture frame 57 is an EN-DC `RRCConnectionReconfiguration` carrying `mobilityControlInfo` to target PCI 90 with a nested NR `reconfigurationWithSync`; the analyzer reports it once as an LTE handover, which is the documented nested-PDML behaviour working on live data. Ticket 02's handover discrimination is no longer fixture-only.
- `scripts/live_analyze.sh` took `$1` as the source whatever it was, so `--kinds cap.pcap` named `--kinds` as the interface and argparse then failed on the pcap. The source is now the first non-option argument, so either order reads.
- Any experiment that suspends dmd or rearranges the USB gadget arms `/data/local/tmp/nasrrc_dm_restore.sh` on the device first, with a delay, so a killed host still puts the phone back. `scripts/experiment_scat_diag.sh restore` runs the same script on demand.

## Fog

- Whether the node tap should replace `live_tail_ring.sh` as the default live path. It is better on every measurement so far, but it has been exercised for minutes, not hours, and nothing yet proves it survives a modem crash or an airplane cycle. Ticket 04.
- Whether the DM session can be started without dmd at all, over the same vendor RIL path dmd uses (`liboemservice.so`, `COMMAND_SET_DM_MODE`). That would remove the one-session-per-boot limit, which neither live path escapes today.
- USB `-u` SDM on this Pixel — blocked on `ro.build.type=user`, not on the start magic.
- Handovers are no longer unobserved, but one sample is thin: a single stationary-UE EN-DC handover to PCI 90. An NR-only `reconfigurationWithSync` that is not nested inside an LTE reconfiguration still has not been seen, and neither has a run of them from a moving UE.
- GSMTAPv3 still cannot be dissected here, but it turned out to matter less than assumed — the NR RRC in a normal session arrives as v2 and dissects. What v3 hides is unquantified.
